# الگوریتم‌های پیشرفته + سیستم سکه + قوانین دقیق عددی
## نسخه ۱.۵ (قابل پیاده‌سازی روی نسخه ۱)

این سند منبع حقیقت برای تمام اعداد، وزن‌ها و قوانین الگوریتمی است.  
عامل کدنویس باید مقادیر را **دقیقاً** همین‌طور که نوشته شده پیاده کند و حدس نزند.

---

## ۱. سیستم سکه (پول مطالعه)

### نام واحد
سکه مطالعه (Study Coin)

### راه‌های کسب سکه (مقادیر قطعی)

| رویداد | سکه | محدودیت |
|--------|------|---------|
| بیدار شدن تا ساعت ۰۷:۰۰ | +۱۵ | فقط یک‌بار در روز |
| بیدار شدن قبل از ۰۶:۴۵ | +۵ اضافی | فقط اگر شرط بالا برقرار باشد |
| تکمیل تمام Taskهای تست مشخص‌شده آن روز | +۴۰ | |
| تکمیل هر Task مطالعه (غیرتست) | +۸ | |
| هر پاسخ درست در تست | +۲ | |
| مرور موفق یک سوال غلط یا نزده (درست جواب دادن در مرور) | +۳ | |
| تکمیل هدف روزانه | +۲۰ | |
| تکمیل هدف هفتگی | +۷۰ | |
| حفظ Streak (هر روز متوالی فعالیت) | +۱۰ | به ازای هر روز Streak |

### قوانین Streak
- اگر در یک روز تقویمی (از ۰۰:۰۰ تا ۲۳:۵۹ به وقت Asia/Tehran) هیچ Task با وضعیت `completed` ثبت نشود → `current_streak = 0`
- در غیر این صورت `current_streak += 1` و در صورت نیاز `longest_streak` به‌روز شود.

### ثبت بیدار شدن
- کاربر باید تا ساعت ۰۷:۱۵ بتواند «بیدار شدم» را ثبت کند.
- بعد از ۰۷:۱۵ دیگر سکه بیدار شدن تعلق نمی‌گیرد.
- زمان ثبت بر اساس timezone کاربر (Asia/Tehran) محاسبه می‌شود.

## ۲. وارد کردن تست‌های قبلی (Past Test Import)

### هدف
کاربر قبلاً تست زده و نباید از صفر شروع کند. باید بتواند نتایج قبلی را وارد کند تا Analytics و Review Queue از همان ابتدا پر شوند.

### جریان کار
1. کاربر یک «جلسه تست گذشته» می‌سازد.
2. مشخص می‌کند: کتاب، node یا test_set، بازه sequence (اختیاری)، parity (اختیاری).
3. سیستم لیست سوالات را نشان می‌دهد.
4. کاربر برای هر سوال یکی از این‌ها را وارد می‌کند:
   - درست
   - غلط
   - نزده
   - (اختیاری) پاسخ نوشته‌شده
5. پس از تأیید نهایی:
   - یک `test_session` با وضعیت `completed` و فلگ `is_imported = true` ساخته می‌شود.
   - تمام `question_attempts` ثبت می‌شوند (append-only).
   - سوالات غلط و نزده وارد `review_queue` می‌شوند.
   - Analytics (Coverage / Accuracy / Volume) بلافاصله به‌روز می‌شود.
   - سکه بابت تست‌های واردشده تعلق **نمی‌گیرد** (چون کار گذشته است).

### قوانین
- `is_imported = true` باید در session ذخیره شود.
- تاریخ جلسه واردشده می‌تواند توسط کاربر مشخص شود (پیش‌فرض: امروز).
- امکان import چند جلسه پشت سر هم وجود دارد.
- بعد از import، سیستم نباید این attemptها را overwrite کند.

## ۳. الگوریتم مرور (Review) — نسخه بهبودیافته

### ورودی
سوالات با وضعیت wrong یا unanswered که در `review_queue` هستند.

### قانون اصلی مرور
- مرور باید **رندوم** باشد (نه به ترتیب sequence).
- سوالات مرور باید از نظر مبحث **نزدیک** به هم باشند، اما ترتیب نمایش تصادفی است.

### تعریف «نزدیک از نظر مبحث»
دو سوال نزدیک محسوب می‌شوند اگر:
- حداقل در یک `node` مشترک در `question_topic_map` باشند، یا
- `node` آن‌ها دارای والد مشترک در عمق حداکثر ۲ باشد (پدربزرگ مشترک یا پدر مشترک).

### الگوریتم ساخت یک جلسه مرور
1. از `review_queue` تا سقف **۲۵ سوال** کاندید انتخاب کن (اولویت: critical > wrong > unanswered).
2. از بین کاندیدها، یک «خوشه موضوعی» بساز (سوالاتی که با هم نزدیک هستند).
3. اگر خوشه کمتر از ۸ سوال داشت، از سوالات نزدیک‌ترین nodeهای مجاور پر کن.
4. ترتیب نهایی نمایش داخل جلسه را **shuffle تصادفی** کن.
5. parity و range در مرور اعمال نمی‌شود (هدف، دیدن دوباره ضعف است).

### مقادیر قطعی
- حداکثر سوال در یک جلسه مرور: **۲۵**
- حداقل مطلوب در خوشه: **۸**
- اولویت Critical: سوالاتی که `wrong_count >= 2`
- فاصله زمانی هدف برای بازگشت Critical: حداکثر **۲ روز**
- فاصله زمانی هدف برای wrong معمولی و unanswered: حداکثر **۳ روز**

### خروج از صف مرور
- اگر کاربر در جلسه مرور به سوال درست جواب دهد → آن مورد از `review_queue` خارج یا وضعیتش به `resolved` تغییر کند.
- اگر دوباره غلط بزند → `priority` افزایش یابد و `scheduled_for` زودتر شود.

## ۴. الگوریتم پیشنهاد تست روزانه (Candidate Generation)

### وزن‌های قطعی اولویت (جمع کل وزن‌ها = ۱۰۰)

| سیگنال | وزن |
|--------|-----|
| هدف موضوعی هفته | ۳۵ |
| ضعف / Review بحرانی | ۲۵ |
| هم‌راستایی با کلاس امروز | ۱۵ |
| parity مخالف آخرین بار | ۱۰ |
| Deadline تکلیف/امتحان (نزدیکی) | ۱۰ |
| هدف تعداد تست | ۵ |

### قانون کلاس‌محور (درخواست کاربر)
اگر در آن روز کلاس دارد:
- حسابان → اولویت تست‌های مرتبط با nodeهای حسابان بالاتر می‌رود.
- شیمی → اولویت شیمی
- فیزیک → اولویت فیزیک

مقدار افزایش اولویت برای درس کلاس آن روز: **+۱۵** به امتیاز نهایی آن کاندید (علاوه بر وزن جدول بالا).

اگر چند کلاس در یک روز داشته باشد، هر کدام به کاندیدهای مربوط به خودشان +۱۵ می‌دهند.

### قانون parity
- اگر برای آن node آخرین parity = odd باشد → پیشنهاد even
- اگر even باشد → پیشنهاد odd
- اگر هیچ سابقه‌ای نباشد → پیشنهاد odd (پیش‌فرض)

## ۵. الگوریتم ظرفیت روزانه

### محاسبه پایه
```
ظرفیت_دقیقه = (ساعت_خواب - ساعت_پایان_مدرسه_یا_کلاس) × ۶۰ - زمان_ثابت_شخصی
```

مقادیر پیش‌فرض:
- ساعت خواب پیش‌فرض: **۲۳:۳۰**
- زمان ثابت شخصی روزانه: **۴۵ دقیقه**
- اگر روز مدرسه باشد و ساعت پایان مشخص نباشد: فرض پایان مدرسه **۱۳:۳۰**

### Override «امروز مدرسه نمی‌روم»
- ظرفیت آن روز × **۱.۳۵** شود (۳۵٪ افزایش).
- حداقل ظرفیت در روز override: **۱۸۰ دقیقه**.

### هشدار Over-capacity
- اگر مجموع `estimated_minutes` کارهای روز > ظرفیت باشد:
  - هشدار نمایش داده شود.
  - هیچ Taskی خودکار حذف نشود.
  - لیست کم‌اولویت‌ترین کارها برای جابه‌جایی پیشنهاد شود.

---

## ۶. الگوریتم هدف هفتگی و هشدار میانی

- روز چک میانی: **چهارشنبه**
- اگر پیشرفت هدف هفتگی < **۵۰٪** باشد:
  - هشدار صادر شود.
  - وزن کارهای goal-critical در پنج‌شنبه و جمعه **۱.۵ برابر** شود.

---

## ۷. الگوریتم انتخاب سوال در تست عادی (Range + Parity)

مقادیر و قوانین قطعی (از قبل موجود + تثبیت):
- parity مجاز: `odd` | `even` | `any`
- اگر تعداد سوال موجود در range + parity < count درخواستی:
  - session ساخته نشود.
  - پیام دقیق: «فقط X سوال با این شرایط وجود دارد.»
- داخل یک session هیچ سوال تکراری مجاز نیست.
- انتخاب نهایی از pool فیلترشده به صورت تصادفی است.
